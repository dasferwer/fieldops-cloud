# Диагностика и восстановление

## Запуск и обновление

```bash
docker compose up --build -d --wait --wait-timeout 180
```

`migrate` завершается после Alembic и демонстрационного заполнения. Два процесса API
запускаются только после его успеха. Миграция журнала добавляет таблицы и не изменяет
существующие заявки. Перед обновлением окружения с ценными данными нужен резервный
снимок PostgreSQL. Проверка восстановления из резервной копии в проект не входит.

Если обновление схемы завершилось ошибкой, прочитайте `docker compose logs migrate`.
Не удаляйте рабочий volume ради повторного запуска. После исправления причины
повторите команду обновления. Демонстрационные пароли меняются в `.env` только для
новых пользователей; существующие записи seed не переписывает.

## Пропали обновления интерфейса

1. Проверьте `curl -f http://localhost:8061/health` и `docker compose logs --tail=50 api`.
2. Сопоставьте REST-запрос с `X-Request-ID`. `realtime_database_unavailable` означает
   потерю доступа к БД; `realtime_timeout` — превышение времени авторизации или отправки.
3. В DevTools проверьте закрытие WebSocket. Коды 4401/4403 требуют повторного входа.
4. После восстановления БД клиент подключится снова. При `reset` он перечитает данные.

Сеть не подтверждает применение интерфейсом: возможны дубли. Источником истины
остаётся REST и PostgreSQL. WebSocket содержит только ID доступных заявок.

## Задержки

`FIELDOPS_REALTIME_POLL_SECONDS` задаёт интервал опроса (по умолчанию 1 секунда),
`FIELDOPS_REALTIME_SEND_TIMEOUT` — предел отправки пакета (5 секунд).
Уменьшение интервала увеличивает число запросов к БД. Сначала измерьте число
подписок, время SQL и ожидание строки `stream_state`; универсальный безопасный
предел числа клиентов здесь не заявляется.

## Очистка журнала уведомлений

По умолчанию `FIELDOPS_STREAM_RETENTION_SECONDS=0`: даже `--apply` ничего не удаляет.
Задайте поддерживаемый срок переподключения в секундах (1–31 536 000) и размер пакета
`FIELDOPS_STREAM_RETENTION_BATCH_SIZE` (1–10 000). Пример суток — технический пример,
а не требование к бизнес-истории:

```bash
docker compose exec -e FIELDOPS_STREAM_RETENTION_SECONDS=86400 api python -m fieldops.retention
docker compose exec -e FIELDOPS_STREAM_RETENTION_SECONDS=86400 api python -m fieldops.retention --apply
```

Первый вызов возвращает JSON dry-run: `candidates`, `delete_through`, текущую границу
`retained_after`. Второй удаляет один пакет и показывает `deleted`. Повторяйте пакеты,
пока `candidates` не станет нулём; каждый пакет — отдельная короткая транзакция.
Фоновая очистка не запускается автоматически. При необходимости оператор запускает
эту же команду своим планировщиком. Пакет берёт блокировку счётчика; при конкуренции
действуют существующие пределы SQL/lock timeout, команду можно повторить.

Клиент с курсором до удалённого префикса получает `reset` и перечитывает REST.
Удалённые сигналы не восстановить без резервной копии. Заявки, их аудит и ключи
повторных команд остаются доступными; текущая версия заявки не зависит от replay.
После первого удаления откат миграции retention отклоняется: старая схема не хранит
`retained_after` и могла бы молча пропустить удалённые сигналы. Отказ происходит до
изменения схемы. Не обнуляйте границу вручную. Для возврата к старой версии потребуется
восстановить согласованный снимок БД до очистки и переподключить клиентов с полной
REST-синхронизацией. Пока удаление не выполнялось, обычный downgrade/upgrade доступен.

## Проверки без удаления рабочих данных

```bash
docker compose --profile test build test
docker compose --profile test run --rm test
docker compose rm -sfv database-test
```

Тестовый сервис использует `fieldops_test`. Проверка миграций отказывается работать
с другим именем БД. Последняя команда удаляет только тестовый контейнер и его том.
`docker compose down` останавливает рабочий стенд с сохранением данных.
