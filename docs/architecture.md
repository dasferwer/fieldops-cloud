# Архитектура FieldOps Cloud

Модульный монолит: `orders.py` отвечает за HTTP-контракт заявок, `services.py` —
за команды и правила, `stream.py` — за журнал уведомлений, `realtime.py` — за
подписку. `main.py` содержит аутентификацию, справочники и агрегаты.
Общение между API-процессами идёт через PostgreSQL; отдельный брокер не требуется.

## Запись и порядок фиксации

Создание сначала захватывает транзакционную advisory-блокировку по пользователю
и ключу повтора. Совпадающий хеш тела возвращает существующую заявку, другой — 409.
Назначение и смена статуса блокируют строку заявки, затем проверяют `version`.
Завершённые состояния не допускают переназначения; в `assigned` переводит команда
назначения, а не произвольная смена статуса.

Заявка, аудит и уведомление фиксируются одним commit. Ошибка уведомления откатывает
всю команду. Номер события выдаёт строка `stream_state`, которую транзакция удерживает
до commit. Обычная PostgreSQL sequence здесь не подходит: поздний commit с меньшим
номером мог бы оказаться позади уже подтверждённого клиентом курсора.
Порядок блокировок: ключ повтора или заявка, затем счётчик журнала.
Внешних сетевых операций внутри этой завершающей части нет.

## Протокол WebSocket

Адрес: `/api/v1/realtime`, без query-параметров. Браузерный Origin должен входить
в `FIELDOPS_CORS_ORIGINS`. После подключения клиент за пять секунд передаёт:

```json
{"token": "JWT", "cursor": 123}
```

При первом подключении `cursor` отсутствует или равен `null`. Сервер отвечает
`connected` с текущей позицией и `reset: true`. Клиент после этого перечитывает
REST-данные: события последующих изменений уже находятся после выданной позиции.
JWT никогда не передаётся в URL. Входной WebSocket-кадр ограничен 8 КиБ настройкой Uvicorn.

Пакет содержит до 100 записей журнала:

```json
{"type": "events", "cursor": 124, "more": false,
 "events": [{"type": "work_order.changed", "id": "UUID"}]}
```

`events` содержит только разрешённые получателю сигналы. Курсор продвигается также
через чужие события; пустой пакет служит контрольной точкой и подтверждением связи.
Числовой курсор отражает позицию общего журнала и не является секретом или правом доступа.

Права определяются текущей записью пользователя и текущим исполнителем заявки.
Прежнему исполнителю разрешён только сигнал `work_order.removed` с уже известным ID.
Ни названия, ни адреса, ни комментарии, ни сведения о новом исполнителе в потоке нет.
Клиент инвалидирует кеш и получает актуальные данные через REST с повторной проверкой прав.

Невозможный курсор или отставание более 10 000 записей возвращает `reset` с новой
позицией. Это требование полной синхронизации, а не незаметный пропуск уведомлений.
Перезапуск API сохраняет журнал; любой другой процесс может продолжить подписку.

## Отказы и безопасность

- Истечение JWT или отключение пользователя закрывает поток кодом 4401.
- Изменение роли закрывает поток кодом 4403; интерфейс очищает кеш и требует входа.
- Неисправная БД закрывает поток кодом 1013. Клиент повторяет подключение с задержкой.
- Медленная отправка ограничена пятью секундами. Соединение БД закрывается до отправки.
- После первого сообщения клиентские данные не принимаются. Ping/pong обслуживает WebSocket.
- При переподключении возможна повторная доставка; сигналы инвалидирования идемпотентны.

Транзакции имеют ограничения ожидания блокировки и SQL-запроса. HTTP-ошибка БД
возвращает 503 с `Retry-After`; клиент должен повторять создание с прежним ключом.
Идентификатор запроса выдаётся в `X-Request-ID`. В структурированных логах нет
тел запросов, паролей, JWT и query-параметров.

Счётчик журнала — общая точка сериализации. Выбранное решение предпочтительно
для небольшого сервиса с проверяемым порядком фиксации; горизонтальное масштабирование
API не устраняет этот предел БД. Автоматическая очистка журнала пока не реализована.
